The IPv6 exclusions follow the [IANA IPv6 special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml). This is a deliberately conservative publisher policy: rare transition/special-purpose public services can be rejected. Ordinary native global IPv6 remains supported. Node's underlying OS DNS request is not forcibly canceled; the caller returns by deadline and a late answer is never admitted.

Session cache removal adds authoritative database lookup per authenticated request. The tests use real Better Auth with isolated in-memory PGlite; they prove local revocation behavior, not production session deployment or database availability.

## Hosting preparation and residual risks

`render.yaml` was validated against Render's public JSON Schema using already installed Ajv 8 and ajv-formats: valid, no validation errors. The first attempt with older root Ajv could not load the schema's draft 2020-12; the rerun used the appropriate installed validator. This is local schema validation, not a connected Render validation or deployment.

The blueprint no longer supplies unsupported `TRUST_PROXY_HOPS=1`; it declares `TRUST_PROXY_ADDRESSES` with `sync:false` for separately verified values. No addresses were invented. Existing live hop-count settings must be reconciled separately before release. Ignoring forwarding headers by default prevents spoofing but can aggregate callers under a proxy's address and throttle legitimate traffic. Trusted ranges need evidence about Render's actual incoming proxy chain; a generic cloud address list is not equivalent to trusted proxy identity.

The blueprint also declares the pre-existing `INTERNAL_API_TOKEN` setting with `sync:false`. Its value must match the web server runtime value. No value was read, generated, changed or rotated. When absent, catalogue rate limiting is explicitly disabled by existing code; if present only on the API and absent on the renderer, all server-rendered callers can share a worker IP rate budget. Cloudflare runtime secret binding is a separate approved operation; placing it in public web build variables would be incorrect.

CI now checks required deployment inputs before executing the deploy command and declares `permissions: contents: read`. Keepalive declares `permissions: {}` because it only sends a public request. Both YAML files parse locally with the expected job and permission structure. No workflow was dispatched. Public SHA/account identifiers are metadata; token values remain secret and are never printed.

Next headers target documents/runtime routes, while Cloudflare `_headers` target ASSETS responses. Both paths need separate verification after an approved deployment. Existing wildcard artwork patterns make an intentional open image optimizer; this agent did not restrict all publisher hosts or redesign artwork serving. Current patched Next/OpenNext versions, private address defenses in their actual deployed image path, size/redirect limits and platform cost limits remain release verification points. No paid binding was added.

The live Render health-path, backup CORS, Cloudflare missing headers and token observations came from the original report. They must be refreshed through separately authorized read-only production checks before release. Source diff or a passing `/health` response cannot prove a job worker is ready or a deployment serves this revision.
